CSS Modules

Having something like:

        const styles = {
          ...sidebarStyles,
          ...subheaderStyles,
          ...filterStyles,
          ...tableStyles,
          ...paginationStyles,
          ...pipelineListStyles,
        };

isn't slow. Next.js doesn't just scan these different CSS style files at runtime, it's resolved at buildtime. When Next.js processes a module.css file, it gives you a plain JS object of name mappings like (for sidebarStyles):

          {
            "sidebar": "sidebar_sidebar__a3Kx9",
            "sidebar-content": "sidebar_sidebar-content__b7Rp2",
            "profile": "sidebar_profile__c1Lm4",
            // ...
          }

These are hashed names, meaning it's an O(1) object key lookup on this pre-built dictionary. So by the time a component runs, "styles" is already a fully resolved JS object sitting in memory.

NEXAUTH SYSTEM

=============================
INDIVIDUAL FILES 

auth.config.ts — Defines authConfig: the bare settings object (providers: [GitHub], session: { strategy: "jwt" }) with no database adapter. Then immediately builds a NextAuth instance from just that config and exports its auth, signIn, signOut. This file imports nothing from Prisma — it's the "safe everywhere" module.

auth.ts — Imports authConfig from auth.config.ts, spreads it (...authConfig) into a second NextAuth() call, and adds adapter: PrismaAdapter(prisma). Exports handlers (used by the NextAuth API route) and its own auth. This is the "full" instance — same providers/session settings as auth.config.ts, plus the DB connection.

proxy.ts — The request gatekeeper that runs on (almost) every request per its matcher. Imports auth from auth.config and uses it to check for a session cookie; if there's no session and the request isn't already for /, it redirects to /.

app/providers.tsx — A one-line Client Component wrapper around SessionProvider from next-auth/react. Exists only because SessionProvider is a React Context provider and must run on the client, but the root layout is a Server Component and can't itself have "use client".

app/layout.tsx — The root layout (Server Component). Renders <Providers>{children}</Providers>, so every page — and everything nested inside it — is inside the SessionProvider context tree.

lib/actions/auth.ts — Defines two "use server" actions, login and logout, that Client Components can call directly. Imports signIn/signOut from auth.config (not auth.ts).

=============================

DEPENDENCY GRAPH


auth.config.ts  (authConfig, auth, signIn, signOut — Prisma-free)
   ├─ used by → proxy.ts            (auth)
   ├─ used by → lib/actions/auth.ts (signIn, signOut)
   └─ spread into → auth.ts

auth.ts  (...authConfig + PrismaAdapter — Prisma-backed)
   ├─ used by → app/api/auth/[...nextauth]/route.ts (handlers)
   └─ used by → app/page.tsx (auth)

app/providers.tsx (SessionProvider)
   └─ used by → app/layout.tsx → wraps every page

lib/actions/auth.ts (login, logout)
   └─ used by → app/LoginButton.tsx, components/sidebar/Profile.tsx
Two things tie this graph together:

Shared authConfig → compatible cookies. auth.config.ts and auth.ts are two separate NextAuth() instances, but because auth.ts spreads authConfig (same providers, same session: { strategy: "jwt" }, same AUTH_SECRET from env), they encrypt/decrypt the exact same session cookie identically. This is why proxy.ts's auth() (from auth.config) can read a cookie that was issued by auth.ts's handlers during the OAuth callback — they're two doors into the same lock.

A Prisma-safety boundary. auth.ts imports PrismaClient, which drags in a 21MB native binary that Turbopack can't bundle outside Server Components/Route Handlers. So:

proxy.ts (compiled as one giant bundle) and lib/actions/auth.ts (reachable from Client Components like Sidebar/Profile) both import from auth.config — never auth.ts.
auth.ts is only imported from app/page.tsx (a Server Component) and the API route (a Route Handler) — the two places where Prisma can be externalized safely.

=============================

The SessionProvider piece is a separate, parallel mechanism: it doesn't talk to proxy.ts/auth.config.ts/auth.ts directly at all. app/providers.tsx → app/layout.tsx just puts a React context in place so that useSession() (used in Profile.tsx) can do a client-side fetch("/api/auth/session") — which itself hits the API route backed by auth.ts's handlers, decrypts the same shared cookie, and returns the user's profile data to the browser.

So at a glance: authConfig is the single source of truth for "what a valid session looks like", shared by both NextAuth instances; proxy.ts and lib/actions/auth.ts use the lightweight instance because of where Turbopack bundles them; app/page.tsx and the API route use the full instance because they're allowed to talk to Prisma; and providers.tsx/layout.tsx just make the cookie-backed session available to client-side useSession() calls anywhere in the tree.

LOGIN/LOGOUT

=============================

Login:

1. GET / — proxy.ts calls auth() (from auth.config) → no cookie → session = null. Pathname is /, so the !== "/" guard is false → proxy passes through. app/page.tsx calls auth() (from auth.ts, fine here — Server Component) → also null → renders <LoginButton />.

2. Click "Login" — LoginButton.tsx is <form action={login}>. Submitting POSTs to /, invoking the login server action in lib/actions/auth.ts.

3. login() calls signIn("github", { redirectTo: "/pipelines" }) — now sourced from auth.config (Prisma-free, since this action is reachable from the client bundle via Sidebar → Profile → lib/actions/auth.ts). It sets CSRF/PKCE cookies and throws a redirect to GitHub's authorize URL. This is the POST / 303 you saw in the logs.

4. GitHub redirects back to /api/auth/callback/github?code=.... This path matches api/auth, so the proxy's matcher excludes it entirely — proxy doesn't run.

5. The request hits app/api/auth/[...nextauth]/route.ts, whose handlers come from auth.ts (full, Prisma-backed). Auth.js exchanges the code, fetches the GitHub profile, and PrismaAdapter writes User/Account rows. Because it's a Route Handler, Prisma externalizes normally — no bundling issue. Since session strategy is "jwt", no Session table row is created; instead Auth.js builds and encrypts a JWT and sets it as the session cookie. Responds with 302 → /pipelines.

6. GET /pipelines — proxy.ts calls auth() (from auth.config) and successfully decrypts the fresh JWE cookie (same secret/strategy as the instance that issued it) → session is truthy → proxy passes through.

7. /pipelines/page.tsx renders. Sidebar → Profile calls useSession() (next-auth/react). The SessionProvider wrapping the app (app/providers.tsx, wired into app/layout.tsx) fetches /api/auth/session client-side (also a Route Handler under auth.ts — Prisma-safe), decrypts the same cookie, and returns { user: { name, image } }, which Profile.tsx displays.


=============================

Logout:

1. User clicks "Sign Out" in Profile.tsx → onClick={() => logout()}, calling the logout server action.

2. logout() calls signOut({ redirectTo: "/" }) — again from auth.config. Since the session is JWT-based, there's no DB row to delete; signOut just clears the session cookie and redirects to /.

3. GET / — proxy.ts's auth() finds no cookie → null, but pathname === "/" so no redirect. app/page.tsx's auth() (from auth.ts) also returns null → renders the login page again. SessionProvider on the client also re-fetches /api/auth/session, gets null, and useSession() reflects the logged-out state everywhere.

4. The key invariant: anything imported by a "use client" component (directly or via a server action) must come from auth.config, never auth.ts — that's the line that keeps Prisma out of bundles where Turbopack can't handle it.

lib/prisma.ts

Line 1 — Imports PrismaClient from the generated Prisma client. The @/generated/prisma/client path is where Prisma outputs the type-safe client after you run prisma generate.

Line 2 — Imports PrismaPg, a Prisma adapter that lets Prisma talk to PostgreSQL using the pg driver instead of Prisma's built-in connection handling.

Lines 4–6 — Casts the Node.js global object to a type that can hold a prisma property. This is the setup for the singleton pattern below — global persists across hot reloads in development.

Lines 8–10 — Creates a PostgreSQL adapter instance using your DATABASE_URL environment variable

Line 12 — The singleton: reuses the existing globalForPrisma.prisma instance if it exists, otherwise creates a new PrismaClient with the adapter. This prevents creating hundreds of DB connections during Next.js hot reloads in development.

Line 14 — In development only, saves the prisma instance onto global so the next hot reload picks it up instead of creating a new one. Skipped in production because the server process never hot-reloads — a new PrismaClient per cold start is fine there.

Line 16 — Exports the single prisma instance so all your lib/data/ files can import prisma from '@/lib/prisma' and share one connection pool.




In depth explanation of line 14:


      In production, Next.js runs as a long-lived server process that starts once and stays running. A new PrismaClient is created when the server boots, and that same instance handles all requests for the lifetime of the process — so there's no problem.

      In development, next dev uses hot module replacement (HMR). Every time you save a file, Next.js re-evaluates the changed module from scratch, which would execute new PrismaClient(...) again — creating a brand new connection pool each time. Do that enough times and you exhaust your database's connection limit (Postgres has a hard cap, often 100).

      global is the escape hatch because it sits outside the module system. HMR tears down and rebuilds modules, but it never touches global. So line 14 says: "in dev, stash the client on global after creating it." Then line 12 checks globalForPrisma.prisma first — if it's already there from a previous hot reload, reuse it instead of creating another one.

      The !== "production" guard on line 14 exists purely to avoid the unnecessary write in production, where global would never be checked again anyway (no HMR, no re-evaluation of the module).


Line 14 works because line 12 reassigns prisma to the global PrismaClient on reloads.

 auth.ts callbacks:

   callbacks: {
    jwt({ token, user }) {
       if (user) token.sub = user.id;
       return token;
    },
    session({ session, token }) {
      if (token.sub) session.user.id = token.sub;
      return session;
    }
  }


jwt callback - runs every time a JWT is created or read (on sign-in, on every subsequent request that touches the session, and on session refresh)
 - user arg is populated once on initial sign-in request. It's the object PrismaAdapter handed back after creating/finding the row in your User table, so user.id is the Prisma cuid.  

On every later request, NextAuth doesn't re-run the adapter lookup — it just decodes the existing JWT, so user is undefined and the if (user) guard skips reassignment. That's why the value needs to be written into token the first time: token is what actually gets encoded into the cookie and persists across requests, while user only exists transiently during sign-in.

token.sub is the conventional JWT field for "subject" (whose identity this token represents) — using it instead of a custom field like token.userId means it lines up with how JWTs are normally structured, and it's the field NextAuth's types already expect you to use for identity.

session callback — runs whenever your app calls auth() (which is happening in your addEnvironment Server Action) or useSession() on the client. Its job is to shape the session object that gets returned to your code. By default, session.user only has name, email, image — NextAuth doesn't put id there automatically. This callback reads the value you stashed in token.sub back in the jwt callback, and copies it onto session.user.id.

You need the JWT callback to persist the id across requests, and the session callback to expose it to session.user.id where addEnvironment() reads it.

Flow:
 1. user signs in via GitHub
 2. PrismaAdapter creates/finds the User row
 3. jwt callback runs with that user, writes user.id into token.sub
 4. token gets encoded into the session cookie
 5. later, your Server Action calls auth()
 6. NextAuth decodes the cookie back into token
 7. session callback runs, copies token.sub into session.user.id
 8. your action reads session.user.id and gets the correct Prisma cuid

AES-256-GCM 

A fixed 256 bit key and a 96 bit nonce (IV) that has a 32 bit counter added to it everytime we put it through AES, where the first nonce (IV) (with a 32 bit counter) is reserved to produce the tag. Once the AES algorithm runs on them, we get a 128 bit scrambled block (a keystream) that we XOR with 1 chunk of a message to create a chunk of a ciphertext. We repeat this process with multiple message chunks until the entire message is converted into a ciphertext.

We have a value “H” computed by putting 128 0 bits into AES, and we use it in a GHASH Chain that essentially multiplies by H and uses XORs with ciphertext to achieve a sequence of bits (a 128-bit hash value) for the Tag. The reserved first nonce (IV) is XORed onto the GHASH result to finish it.

On decryption, recompute the entire GHASH chain over the received ciphertext, XOR in the reserved first nonce (IV) to build a copy of the Tag to compare against the one that arrives. If the ciphertext was changed, it rejects (doesn't decrypt the ciphertext) the arrived Tag.

The last message chunk entered is typically smaller than 128 bits, so it just XORs with the first part of that block's keystream and discards leftovers, meaning the ciphertext ends up being the same length as the message.

GCM chops up your message into 128 bit blocks each (where last message can be shorter, as said in paragraph above)

The 32-bit counter gives AES a different input block for every chunk of your message so that each chunk gets it own unique keystream. Without the counter, you would have the same keystream being XORed with different message chunks, which breaks the encryption. 

The counter keeps different chunks within one message from colliding, while the nonce (IV) keeps different messages (NOT chunks of one) from colliding.

If the same key and nonce (IV) are used for 2 different messages, the keystream repeats, meaning an attacker who knows one plaintext can XOR their way to the other plaintext (but not get the key). However, if the counter was different for those 2 messages, then it wpuld be safe.

For each message, the counter sequence (32-bits) is always the same. What makes each message's keystream unique is the nonce (IV) it's paired with.

The tag, iv, and ciphertext are made public. The only way someone can get plaintext is if they had the 256-bit key. 

The 256-bit key:
- Generates each keystream block that gets XOred with the message chunks
- Derives H 
- Produces the reserved first nonce, used to finish the tag





AAD (additional authenticated data) is data you want to keep readable but protect from tampering. It's guarded by the Tag, and if added, is used in the GHASH chain at the very start, multiplied by H. 


2 Uses of AAD:

Database fields: Encrypt a user’s account balance, and put that user’s ID in the AAD. Now an attacker with write access to the database can’t copy user A’s encrypted balance into user B’s row — decryption there recomputes the tag with B’s ID as AAD, even though A's ID is in the AAD, meaning it won’t match, and it’s rejected. The ciphertext is cryptographically nailed to user A.

Encrypted files: Put the filename or a version number in AAD so one valid encrypted file can’t be silently swapped for another.

Explanation on why 'SecretModalWithEnvironments' in SecretModalController didn't call onCreate() or onSave() properly, but Environment and Pipeline Modals did call:


The difference comes down to component identity, not behavior — the four controllers all render structurally similar JSX, but only SecretModalController created a new component on every render.

The other two (working):


return <CrudModalController mode={mode} record={pipeline} ... ModalComponent={PipelineModal} />;
PipelineModal is a reference to a function declared once, at module scope, in PipelineModal.tsx. No matter how many times PipelineModalController re-renders, PipelineModal is the exact same function object every time. React identifies component types by reference equality — same reference in → React treats it as "the same component, just re-render it with new props," preserving all of its internal hook state across renders.


SecretModalController (broken):

        const SecretModalWithEnvironments = (props) => (
          <SecretModal {...props} environments={environments} />
        )
        return <CrudModalController ... ModalComponent={SecretModalWithEnvironments} />;


This arrow function is defined inside SecretModalController's body. Every time that body runs, JavaScript allocates a brand-new function object — even though the code looks identical each time, it's a different reference. When CrudModalController renders <ModalComponent .../> and sees the type changed from the previous render, React doesn't update in place — it unmounts the old SecretModal instance entirely (discarding all its hook state: query, selectedEnvId, and the useActionState results) and mounts a fresh one from scratch.

Why that timing was fatal specifically for save/create: addSecret/updateSecret both call revalidatePath('/secrets'). Next.js ties that to a router refresh of app/secrets/page.tsx, which hands SecretModalController new environments/secret props right as the action resolves — causing exactly the re-render that manufactures a new SecretModalWithEnvironments identity, right when useActionState's state was transitioning to 'success'. The remount reset everything back to {status: 'idle'} before the useEffect watching for 'success' ever got to run, so onCreate()/onSave() silently never fired. PipelineModal/EnvironmentModal/WebhookModal go through the identical revalidatePath → refresh → re-render sequence, but since their component reference never changes, React just updates props in place and the in-flight useActionState result survives to be observed by the effect.

The fix (already applied) removes the inline wrapper and passes environments through a new extraProps param on CrudModalController, so SecretModal itself — a stable, module-level reference — is used as ModalComponent, matching the other three.

Explanation on 'env', used with child_process.spawn()

"
  const env = { ...process.env, ...Object.fromEntries(job.data.env.map(({ key, value }) => [key, value])) };
"

Step 1 — job.data.env.map(({ key, value }) => [key, value])

      .map walks the array and, for each { key, value } object, destructures it and returns a 2-element tuple [key, value].


      [{ key: "TARGET", value: "prod" }]
            ↓
      [["TARGET", "prod"]]
      If there were multiple env vars, e.g. [{key:"TARGET",value:"prod"}, {key:"REGION",value:"us-east-1"}], you'd get [["TARGET","prod"], ["REGION","us-east-1"]] — a list of key/value pairs.


Step 2 — Object.fromEntries(...)

      Object.fromEntries takes that array of [key, value] pairs and builds a plain object out of them — the inverse of Object.entries.


      [["TARGET", "prod"]]
            ↓
      { TARGET: "prod" }


Step 3 — { ...process.env, ...<that object> }

      This spreads two objects together, later keys winning on collision:

      ...process.env — copies in every variable from the current Node process's environment (PATH, HOME, etc.), so the shell spawned by spawn still works normally.
      ...{ TARGET: "prod" } — layers the job-specific vars on top, overwriting any pre-existing variable of the same name.

      So the final env passed to spawn looks like:

          {
            PATH: "C:\\Windows\\system32;...",   // inherited from process.env
            HOME: "C:\\Users\\...",              // inherited
            // ...everything else in process.env...
            TARGET: "prod"                        // added by the job
          }

Why it's needed at all: job.data.env is stored as an array of { key, value } objects (matching the Prisma/pipeline config shape in types.ts:60), but Node's spawn env option expects a plain Record<string, string> (NodeJS.ProcessEnv). The map + fromEntries chain converts the array shape into the object shape spawn requires, and the spread merges it with the current process environment instead of replacing it entirely

Explanation on "graphJson as unknown as Prisma.InputJsonValue" 


await prisma.pipelineDefinition.update({
  where: { id: latest.id },
  data: { graphJson: graphJson as unknown as Prisma.InputJsonValue, configJson, createdById },

graphJsonInput is just graphJson with a cast to Prisma.InputJsonValue. Although graphJson is deserialized through 'toDefinition()', it still holds nodes of type 'CustomNode', which is why we need that cast. 

Why the cast: Prisma types a Json column as InputJsonValue, whose object arm is { readonly [key: string]: InputJsonValue | null } — an index signature. GraphJson has named properties, so TypeScript checks each one against that signature recursively, and nodes: CustomNode[] fails. 

CustomNode is built on React Flow's Node, which declares non-JSON fields:

        export type Node<...> = NodeBase<...> & {
            style?: CSSProperties;
            domAttributes?: Omit<HTMLAttributes<HTMLDivElement>, ...>;  // event handlers
        };

so TypeScript can't see GraphJson as an InputJsonValue even though toDefinition only ever builds plain data.

ConfigJson is fine since it's a Record<string, StageConfig>, which already has an index signature and bottoms out in primitive types.

An index signature declares the shape of keys rather than naming them, like 'key: string'. 
 - Record<K, V> means "{ [key: string]: string[]}
 - ConfigJson has an index signature where a node id (a string) maps to a StageConfig type with named keys (command, timeout, retries)

TYPESCRIPT SPREAD OPERATOR

@/lib/data/secret.ts has getSecretById(), with return types that omit 'encryptedValue', 'iv', and 'authTag'. 

If, in the return statement, you return '...secret', it actually returns the encryptedValue, iv, and authTag despite them not being in the return type because '...secret' carries the other types, meaning TypeScript allows excess properties on variables using the spread operator.

The solution is to omit them by using something like: 
  const { encryptedValue: _ev, iv: _iv, authTag: _at, ...rest } = secret;

and then return '...rest'

Ex:

    type Row    = { id: string; name: string; secretBlob: string };
    type Public = Omit<Row, 'secretBlob'>;
    declare const row: Row;

    const a: Public = { ...row };                    // ✅ no error
    const b: Public = { ...row, secretBlob: 'x' };   // ❌ TS2353
    const c: Public = { id:'1', name:'n', secretBlob:'x' }; // ❌ TS2353
    const d: Public = { ...row } as const; // via a variable → ✅ no error

    const deadline = setTimeout(() => {
      timedOut = killTree(child, false);
      if (!timedOut) return;

      graceTimer = setTimeout(() => killTree(child, true), KILL_GRACE_MS);

      graceTimer.unref();
    }, timeoutMs);

Once a process times out, we must kill it.

killTree(child, false) - 'false' gives a SIGTERM signal, which sets the graceTimer for 5 seconds.
 - SIGTERM politely requests for a process to stop, allowing it to clean up its resources within 5 seconds

killTree(child, true) - 'true' gives a SIGKILL signal, which forcefully kills the process, called if the process didn't clean up in the 5 seconds.
 - 'SIGKILL' is executed directly by the kernel to terminate  aprocess immediately, preventing any cleanup or saving.

graceTimer.unref() - prevents timeout from being reason runner refuses to exit at shutdown by removing the timeout from the event loop
 - Without this, the runner would have to wait the full timeout out (5 seconds) before shutting down.

Once 'SIGTERM/SIGKILL' trigger the process to cleanup, the process calls the 'close' event (child.on('close')) before terminating
 - This means 'finish()' is called after 'deadline' executes

killTree():

The difference between the 2 if statements is reliant on whether 'detached' is set to true

if process.platform === 'win32', detached is set to false
else if process.platform is on POSIX, detached is set to true

On POSIX the negative pid signals the process group, which `detached: true` above created. 

On Windows, taskkill /T walks the tree by pid; there is no meaningful graceful stage there, so `force` is
ignored and the second call (in the graceTimer timeout) simply finds nothing left to kill.

============================================================================================



        function killTree(child: ChildProcess, force: boolean): boolean {
          if (child.pid === undefined) return false;

          try {
            if (process.platform === 'win32') {
              if (child.exitCode !== null || child.signalCode !== null) return false;

              const killer = spawn('taskkill', ['/pid', String(child.pid), '/T', '/F'], {
                windowsHide: true,
                stdio: 'ignore',
              });
              killer.on('error', () => { });
              killer.unref();
            } else {
              process.kill(-child.pid, force ? 'SIGKILL' : 'SIGTERM');
            }

            return true;
          } catch {
            return false;
          }
        }


1st case: process.platform !== 'win32':
 - In 'deadline', the first call to killTree makes force false. This sets the signal in process.kill() to SIGTERM
      - This gives the process 5 seconds to terminate before calling killTree with force: true, setting the signal to SIGKILL

 - killTree(child, false) sets the child process's signal to SIGTERM. 
 - If you had the "if (child.signalCode !== null)" guard before the try {} statement, for POSIX platforms, it would incorrectly return false because:

          Under shell: true the direct child is the shell. 
          The shell installs no signal handlers, so the graceful SIGTERM at the deadline always kills it instantly and sets child.signalCode. 
          When the real command handles SIGTERM itself, it survives as a grandchild — and 5s later the grace timer's killTree(child, true) hit that guard, returned false, and never sent SIGKILL. 
          The command lived on holding the stdout pipe, so the 'close' event doesn't fire
          
          The SIGTERM went to the whole process group, not just the shell.

          process.kill(-pid, 'SIGTERM') signals every process in the group, so Node received it too — it just had process.on('SIGTERM', () => {}) installed and ignored it. The shell had no handler, so it died. 
          Node then reaped the shell and set child.signalCode = 'SIGTERM'.

          So that guard was reading the shell's death and concluding the tree was gone, at the exact moment the tree provably wasn't.



2nd case: process.platform === 'win32':
 - On the first call -- killTree(child, false), Windows kills the child process and its children.
 - This means tha the second call -- killTree(child, true) typically doesn't ever call, but it definitely can

 - The reason the guard is there -- if (child.exitCode !== null || child.signalCode !== null) return false : 

          Windows recycles pids, so without the guard you risk killing an unrelated process.

   Example:
      1.  0ms   - Stage A spawns cmd.exe pid 14312
      2.  250ms -	deadline → taskkill /pid 14312 /T /F → tree dies, exitCode set, handle closed, 14312 freed
      3.  ~2s   -	Stage C (unrelated, healthy) spawns a build step — Windows hands it 14312

Extra Info on: process.kill(-child.pid, force ? 'SIGKILL' : 'SIGTERM');
 /*
  * Deliberately not guarded on the child's exit state, the way the Windows branch is.
  * The direct child is the *shell*, and it is the first thing to die: it installs no
  * handlers, so the graceful SIGTERM always takes it down, setting child.signalCode
  * immediately. A command that handles SIGTERM itself outlives it — which is the only
  * situation the escalation exists for. Reading signalCode as "the tree is gone" would
  * therefore suppress the SIGKILL in exactly the case that needs it, leaving the real
  * command alive, still holding the run's workspace and the stdout pipe that 'close'
  * is waiting on.
  *
  * The group is its own liveness test: a process group outlives its leader as long as
  * any member is left, and signalling an empty one throws ESRCH, which the catch below
  * reports as "there was nothing to kill".
  */

The retry row is opened BEFORE the failure is recorded, and the order is load-bearing.

loadRunContext folds stage rows last-write-wins over ascending attempt, so the stage's
reported status is whatever its highest attempt says. Writing FAILED first leaves a
window in which that is the latest word — and the other four worker slots are live. A
sibling finishing in that window calls advanceRun, runOutcome sees a failure-terminal
stage, and the run is finalized FAILED with cancelPendingStages sweeping behind it. The
retry then lands as an orphan row in a run nothing will ever advance again: the
configured retry silently never happens.

Opening attempt N+1 first means the stage goes straight from RUNNING to PENDING as far
as any reader is concerned, and runOutcome never sees the failure at all. A crash
between the two leaves attempt N stuck RUNNING, which is harmless — it is no longer the
latest attempt — and is exactly what the boot reaper is for.
